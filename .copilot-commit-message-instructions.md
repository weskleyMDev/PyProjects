# Commit Message Instructions

Generate commit messages following the Conventional Commits specification.

## Format

Use the following format:

<type>(<scope>): <description>

The scope is optional.

Examples:

- feat(auth): add JWT authentication
- fix(api): handle invalid request parameters
- refactor(users): simplify user service
- test(auth): add login integration tests
- docs(readme): update installation instructions
- chore(deps): update project dependencies

## Allowed Types

Use one of the following types:

- feat: A new feature or functionality
- fix: A bug fix
- refactor: Code changes that neither fix a bug nor add a feature
- perf: A performance improvement
- test: Adding or modifying tests
- docs: Documentation-only changes
- chore: Maintenance tasks that do not modify application behavior
- build: Changes to the build system or dependencies
- ci: Changes to CI/CD configuration

## Rules

- Choose the type based on the primary purpose of the changes.
- Use a scope when it clearly identifies the affected project, module, component, or area.
- Keep the description concise and specific.
- Describe what changed, not why it changed.
- Use the imperative mood.
- Do not capitalize the first letter of the description.
- Do not end the description with a period.
- Do not include unnecessary details.
- Do not mention files, unless doing so is useful to understand the change.
- Do not add a body or footer unless the changes require additional context.
- Prefer a single concise commit message.
- Do not invent information that cannot be inferred from the changes.

## Breaking Changes

If the changes introduce a breaking change, append `!` after the type or scope.

Examples:

- feat!: remove legacy authentication API
- refactor(api)!: change response format

Only use `!` when the change actually breaks backward compatibility.

## Language

Write commit messages in English.
